Build instructions for Oaklisp
==============================

Prerequisites
=============

- GCC or Clang
- GNU Make
- Autoconf (>= 2.69) and Automake

Optional:
- LaTeX (texlive, latexmk) for building documentation
- gcc-multilib / glibc-devel.i686 for 32-bit mode on a 64-bit host
- Guile 3 (guile-3.0) to bootstrap from source alone, without prebuilt/

Quick Start
===========

	autoreconf --install
	./configure
	make
	make install

On a 64-bit host this builds a native 64-bit Oaklisp with 62-bit
fixnums.  Oaklisp is self-hosting, so the build has to bootstrap
somehow (see Bootstrapping below); configure picks the first of
these that it finds:

- a world image in prebuilt/ (the "master" branch has it) or an
  installed Oaklisp: nothing beyond a C compiler is needed;
- Guile 3: builds from source alone, which is how the "devel" branch
  and release tarballs -- neither of which carries prebuilt/ -- are
  built.  Takes a few minutes longer.

For further details read INSTALL generated by running autoreconf.

Configure Options
=================

Option                    Default   Description
------------------------  -------   -----------
--enable-64-bit           yes       Native 64-bit mode
--disable-64-bit                    Force 32-bit (-m32)
--enable-docs             yes       Build LaTeX documentation
--enable-ndebug           yes       High-speed mode (sets -DFAST)
--enable-threads          no        Native threads with concurrent GC
                                    (experimental; see below)
--with-compile=METHOD     check     How .oak sources become .oa bytecode:
                                    world, prebuilt, guile, or check for
                                    the first available in that order
--with-cold-link=METHOD   check     How the cold world is linked: world
                                    (tool.oak in the bootstrap world), c
                                    (oak-cold-linker), guile (tool.oak in
                                    the Guile host); check: world when
                                    compiling with one, else c
--with-world[=PATH]       search    Bootstrap world image ("no": none)
--with-oaklisp=OAK        no        Existing emulator to run the bootstrap
                                    world with (default: the one being built)
--with-bytecode[=DIR]     search    Prebuilt .oa files ("no": none)
--with-guile[=GUILE]      search    Guile 3 interpreter for the hosted
                                    Oaklisp ("no": none)

See ./configure --help for details.

What Gets Built
===============

Two components:

file          | purpose
--------------|----------------------------------------------
oaklisp       | the executable / emulator / virtual machine
oakworld.bin  | pre-built Oaklisp system (read in by the executable)

The world is built in stages from .oak source files:

	new.cold        Cold world (core runtime)
	oakworld-1.bin  Warm boot
	oakworld-2.bin  + macros, bignums, rationals, I/O
	oakworld-3.bin  + compiler (in compiler-locale)
	oakworld.bin    + Scheme compatibility (in scheme-locale)

Architectures
=============

From Oaklisp's point of view a machine is characterized by

* the size of a reference (word size) in bits, 32 or 64, which
  determines the fixnum range (30 or 62 bits);
* the number of 16-bit instructions packed into each reference,
  currently always 2 (on 64-bit machines the other half of each
  reference in a code vector is unused);
* the byte order, which matters only for binary world images and the
  running emulator.

These are named as follows, and the names are used for the
subdirectories of prebuilt/, for the --target option, and in the
header lines described below:

	bc2-32     bytecode, 2 instructions per ref, 32-bit refs
	bc2-64     bytecode, 2 instructions per ref, 64-bit refs
	bc2-el32   world/emulator, little-endian 32-bit
	bc2-eb32   world/emulator, big-endian 32-bit
	bc2-el64   world/emulator, little-endian 64-bit
	bc2-eb64   world/emulator, big-endian 64-bit

Compiled bytecode (.oa files) is independent of byte order, and in
practice of word size too, since the compiler does not fold constants
whose value would depend on it; the word size in the name records
the fixnum range the file's integer constants are assumed to fit,
so bc2-32 bytecode can be used anywhere.  Cold worlds (.cold, the
hex text produced by the cold linkers) are byte-order independent
but word-size specific.  Binary worlds (.bin) are specific to byte
order and word size.

Each of these files begins with a header line identifying what it is
for, which the emulator, the loader, and the linkers check:

	;oaklisp-bytecode word-size=32 instructions-per-ref=2
	;oaklisp-world format=cold word-size=64 instructions-per-ref=2
	;oaklisp-world format=binary endian=little word-size=64 instructions-per-ref=2

Files without a header (from before this scheme) are accepted and
assumed to be bc2 bytecode, or, for binary worlds, are identified by
their old magic bytes.

Within a running system the architecture is available as
`host-architecture`, and the compiler generates code for the fluid
`#*target-architecture`, which defaults to the host and is set by
the --target command line option:

	oaklisp -- --target bc2-32 --compile myfile --exit

Bootstrapping
=============

Oaklisp is self-hosting: the compiler and most of the runtime are
written in Oaklisp, so building the world from .oak source requires a
running Oaklisp.  There are two ways to break the circle.

From source alone, with Guile 3: the Guile-hosted Oaklisp in
src/cold-compiler/ loads the world's own macros and compiler from the
.oak sources and runs them, so the .oa objects, and the cold world
(via tool.oak), come straight from the sources.  This is what the
"devel" branch and the release tarballs made by "make dist" rely on,
since neither carries prebuilt/; it is also how the Debian package is
built.  Nothing is lost by it: the compiler is deterministic, so the
objects are byte for byte what a native Oaklisp produces.

With prebuilt material: the prebuilt/ directory, kept on the "master"
branch of the git repository (not on "devel", and not in tarballs),
holds two kinds of bootstrap material, arranged by architecture:

	prebuilt/src/world/bc2-32/*.oa          compiled bytecode
	prebuilt/src/world/bc2-el32/oakworld.bin world images
	prebuilt/src/world/bc2-eb32/oakworld.bin
	prebuilt/src/world/bc2-el64/oakworld.bin
	prebuilt/src/world/bc2-eb64/oakworld.bin
	prebuilt/src/emulator/instr-data.c      instruction names for debugging builds
	prebuilt/doc/                           documentation PDFs

Two steps need a running Oaklisp, or a stand-in for one, and
configure chooses how to do each (--with-compile, --with-cold-link):

* Compiling .oak to .oa.  With a *world*: if a world image for the
  emulator being built is found (in prebuilt/, or installed on the
  system, or given with --with-world=PATH), the sources are compiled
  by it, run by the emulator being built (or by --with-oaklisp).  The
  freshly compiled assembler is loaded into that world first, so an
  older world can compile sources that use instructions it does not
  know.  With *prebuilt* bytecode: the .oa files in prebuilt/ are
  used as they are.  With *guile*: the Guile-hosted Oaklisp in
  src/cold-compiler/ (see its README) loads the world's own macros
  and compiler from the sources and runs them; this needs nothing
  but Guile 3 and a C compiler, and takes a few minutes.

* Linking the cold world.  tool.oak, the Oaklisp linker, either in
  the bootstrap *world* or in the *guile* host, or oak-cold-linker,
  a standalone *C* reimplementation of it built alongside the
  emulator.

The newly built emulator then boots the cold world and loads the
remaining layers.  By default a world is used for both steps when one
is found, otherwise prebuilt bytecode and the C linker, and failing
that Guile.  The result is the same whichever way is chosen: the
compiler is deterministic and reaches a fixpoint, so every route
produces the same objects and all three linkers produce identical
cold worlds ("make check" verifies this).

For example, to insist on building from source alone on a machine
with Guile, even if a world or prebuilt bytecode is around:

	./configure --with-compile=guile --with-cold-link=guile

One thing the Guile host cannot do is generate src/emulator/instr-data.c,
the instruction name table that only a debugging emulator
(--disable-ndebug) compiles in.  It is generated by the world just
built (and shipped in tarballs), so a debugging build from a bare
source tree needs a world (--with-world) or prebuilt/ for that one
file; the default high-speed build does not use it.

To build for one word size using an existing Oaklisp of another,
e.g. a 32-bit system on a 64-bit machine with a 64-bit Oaklisp
installed:

	./configure --disable-64-bit --with-oaklisp=/usr/bin/oaklisp \
	            --with-world=/usr/lib/oaklisp/oakworld.bin

The bootstrap system compiles everything with --target bc2-32 and
links the cold world for it, and the new 32-bit emulator boots it.
(A bootstrap world from before the --target option can still be
used, since the bytecode it generates is the same.)

Building for another byte order requires a cross compiler and a way
to run the resulting emulator, e.g. qemu-user with binfmt support:

	./configure --host=s390x-linux-gnu CC=s390x-linux-gnu-gcc LDFLAGS=-static

Since there is no big-endian world in prebuilt/ for that word size
this bootstraps from bytecode.  (oak-cold-linker is currently built
with the same compiler as the emulator, so it too runs under qemu.)

Refreshing prebuilt/
====================

"make dist" leaves prebuilt/ out of the tarball on purpose: releases
are built from source with Guile (or from an installed Oaklisp),
and the material is several megabytes that would go stale.

After building, "make prebuilt" recompiles all the sources for
bc2-32 into prebuilt/src/world/bc2-32/, copies the world just built
to prebuilt/src/world/ARCH/oakworld.bin for this machine's
architecture, and refreshes instr-data.c and (if enabled) the PDFs.
The pieces are available separately as "make prebuilt-bytecode" and
"make prebuilt-world" in src/world/, and "make prebuilt" in
src/emulator/ and doc/.  The prebuilt worlds for other architectures
have to be made on (or emulated for) those machines.

Testing
=======

	make check          run the test suite in tests/ (a few minutes)
	make bench          run the benchmarks in tests/bench.sh

The test suite exercises the language, the compiler, world images,
and checks that the world reproduces its own objects, that all cold
linkers agree, and (when Guile is present) that the Guile-hosted
compiler reproduces the objects too.  Failures are detailed in
tests/NAME.log.  "make bench" prints best-of-five CPU times for ten
small benchmarks; see tests/bench.sh for saving and comparing runs.

Thread Support
==============

	./configure --enable-threads

builds the emulator with native (pthread) threads and the concurrent
mark-sweep collector they require (-DTHREADS -DUSE_MARK_SWEEP), which
is off by default.  Green threads (DELAY, FUTURE, PROCESS-RUN-FN)
work without it.  The state of native threads is experimental: once
--pthreads N has initialized them, code that invokes the compiler
deadlocks on the guard mutexes, and even precompiled code is not
reliable; see Threads.md.  The option also costs performance when
threads are not in use, almost all of it from the mark-sweep
allocator rather than the thread support itself.  Measured with
"make bench" on the same world (ratio of CPU time to the default
build):

	                  -DTHREADS   -DUSE_MARK_SWEEP   both (--enable-threads)
	tak                  0.95           1.04              1.11
	fib                  1.04           0.99              1.06
	bignum               0.99           1.00              1.15
	sort                 1.03           1.17              1.63
	cons                 0.98           1.00              1.30
	strings              0.98           1.07              1.09
	hash                 1.09           0.99              1.06
	dispatch             0.97           0.96              1.00
	eval                 1.07           1.04              1.16
	format               1.03           3.39              4.90

Running Oaklisp
===============

	# Interactive REPL
	oaklisp

	# With explicit world
	oaklisp --world /path/to/oakworld.bin

	# Evaluate and exit
	oaklisp -- --eval '(+ 1 2)' --exit

	# Compile a file
	oaklisp -- --compile myfile --exit

	# Compile a file for another architecture
	oaklisp -- --target bc2-32 --compile myfile --exit

	# Load a file
	oaklisp -- --load myfile --exit

Emulator options go before --, Oaklisp options go after.
"oaklisp --version" reports the emulator's architecture.

Debian Packages
===============

	dpkg-buildpackage -us -uc

Produces two packages:
- oaklisp      -- emulator + world + man page
- oaklisp-doc  -- PDF documentation + examples

Troubleshooting
===============

"no way to compile the world"
    Configure found neither a world image for this architecture, nor
    prebuilt bytecode, nor Guile 3.  Install Guile 3 (guile-3.0; or
    point at one with --with-guile=PATH) to build from source alone,
    or get the prebuilt/ directory from the "master" branch, or point
    configure at an installed Oaklisp with --with-oaklisp=PATH and
    --with-world=PATH.

"world ... is for bc2-el32 but the bootstrap emulator is bc2-el64"
    The world given with --with-world does not match the emulator
    that will run it.  Give a matching pair with --with-oaklisp and
    --with-world, or let configure search.

"... has 4 instructions per ref, target has 2"
    Bytecode for a different instruction packing cannot be used.

"Integer constant N does not fit in a 30-bit fixnum"
    A file destined for the cold world contains an integer literal
    that is not a fixnum on the target; cold worlds cannot contain
    bignums.  Rewrite the expression, as print-integer.oak does.

32-bit build fails with missing headers
    Install 32-bit development libraries:
    sudo apt install gcc-multilib      (Debian/Ubuntu)
    sudo dnf install glibc-devel.i686  (Fedora/RHEL)

Out of memory with --size-heap
    The argument is in units of 1024 refs.  On 64-bit, each ref is 8
    bytes, so --size-heap 4096 means ~32 GB.  The default (~1 MB) is
    fine for most use.
